# Multi-Agent Concurrency Benchmark

Comparative benchmark of three execution architectures in `lispm-agent` + `lispm-kernel` across 8, 24, and 32 concurrent tool-using agents.

All numbers below are medians across 4 rotated repeats per agent count recorded in `docs/agent-benchmark.json` (generated by `make bench-agents` / `scripts/bench-agents.py` driving `bench/agent-control-plane.el`). As with `docs/benchmark.md`, repeating a 2 ms timer inside batch Emacs measures **event-loop blocking and scheduler responsiveness**, not GUI input-to-paint latency.

## Environment & Harness

- **Machine**: `macOS-27.0.1-arm64-arm-64bit-Mach-O` (`arm64`, 10 CPUs)
- **Emacs**: GNU Emacs 31.1 (`emacs -Q --batch`)
- **Kernel binary**: `build/lispm-kernel` (`SBCL 2.6.9`)
- **Agent counts & repeats**: `8, 24, 32` concurrent agents × `4` repeats, rotating mode order (`elisp`, `kernel-sse`, `kernel-actors`) across repeats
- **Mock SSE stream**: multi-threaded Python `HTTP/1.1` SSE server (`0.5 ms` per chunk delay)

### Four-Step Workload per Agent

Every concurrent agent (`bench-00`..`bench-(N-1)`, 1 `:visible` viewport and `N-1` `:hidden` viewports) executes a real multi-step `(lispm-tell ...)` turn through `lispm-turns`:

1. **Step 1**: 16 thinking deltas + 8 text deltas + streamed `run_shell` call (`input_json_delta` in 64-byte chunks, ~3.8 KB padded command).
2. **Step 2**: 8 thinking deltas + parallel `search_files` and `read_file` calls against a temporary Git repository.
3. **Step 3**: 8 text deltas + `edit_buffer` replacing `OLD` with `NEW` in dedicated live Emacs buffer `bench-buf-XX` (exchanging bi-directional Editor Effect RPC in `kernel-actors`).
4. **Step 4**: 24 text deltas producing the final completion reply.

Every run verifies that all `N` agents finish `idle`, contain all 4 `** DONE ...` Org transcript entries, and mutated their target Emacs buffer cleanly.

### Modes Compared

| Mode | HTTP / SSE Stream | `search_files` / `run_shell` | Multi-Step Loop | Delta Coalescing & Viewport Filtering |
|---|---|---|---|---|
| `elisp` | Emacs `curl` + Elisp SSE | Emacs processes | Elisp (`lispm-turns`) | No |
| `kernel-sse` | `lispm-kernel` `llm-stream` | `lispm-kernel` jobs | Elisp (`lispm-turns`) | No per-turn actor suppression |
| `kernel-actors` | `lispm-kernel` `P_agents` (`llm-stream`) | `lispm-kernel` (`agent-tools`) + Editor RPC | `lispm-kernel` `P_agents` | Yes (`N-1` `:hidden`, outbox credit control) |

## Key Findings

1. **Emacs remains under 60 Hz frame budget only with `kernel-actors` at 24–32 agents**:
   - Pure `elisp` degrades from `5.34 ms` p95 / `117.18 ms` p99 at 8 agents to **`60.19 ms` p95 / `238.96 ms` p99** at 24 agents and **`60.26 ms` p95 / `393.90 ms` p99** at 32 agents.
   - `kernel-sse` keeps p95 low (`4.13–4.26 ms`) by offloading JSON/SSE parsing, but still blows past 16 ms at the 99th percentile (`31.17 ms` at 24 agents, `46.61 ms` at 32 agents) because uncoalesced frames trigger frequent Emacs turn orchestration.
   - `kernel-actors` maintains **`1.49 ms` p95 / `7.63 ms` p99** at 24 agents (**40.4×** / **31.3×** lower than `elisp`) and **`1.33 ms` p95 / `8.48 ms` p99** at 32 agents (**45.3×** / **46.5×** lower than `elisp`; **3.2×** / **5.5×** lower than `kernel-sse`).

2. **Viewport coalescing & bounded backpressure cut IPC pressure sharply**:
   - At 32 agents, `kernel-actors` sends **`851.0`** wire frames to Emacs versus **`2438.5`** in `kernel-sse` (**2.87× fewer** frames).
   - Kernel outbox queue peaks drop from **`7507.5`** (`kernel-sse`) to **`220.0`** (24 agents, **34.1× lower**) and **`137.5`** (32 agents, **54.6× lower**) under credit-based backpressure.
   - Emacs GC pause time at 32 agents drops from **`238.78 ms`** (`elisp`) to **`145.59 ms`** (`kernel-actors`, **39.0% reduction**).

3. **Honest trade-offs and remaining sources of `max lag`**:
   - Total batch `wall_ms` against a 0.5 ms-per-chunk local mock server is higher in `kernel-*` (`10.69 s` vs `6.60 s` at 32 agents) because each step traverses IPC queues, kernel reactor workers, Editor Effect RPCs, and cooperative 5 ms pump intervals instead of monopolizing Emacs's event loop via unthrottled process filters.
   - The `max_lag` spike (`680–1359 ms` across all three modes) and baseline `stalls_over_16ms` originate primarily on Emacs's own initial synchronous setup (`(require 'org)` and opening `N` Org session buffers on initial `lispm-tell`) and per-turn Org buffer writes / `lispm-request-body` serialization rather than SSE streaming.

## Reproduce

```sh
make bench-agents \
  LISPM_AGENT=../lispm-agent/lisp \
  LISPM_UI=../lispm-ui \
  LISPM_AUTH=../lispm-auth \
  BENCH_AGENTS=8,24,32 \
  BENCH_REPEATS=4
```
